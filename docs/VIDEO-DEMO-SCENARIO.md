# DataKeeper C/S/O 5분 데모 녹화 시나리오

> 60초 본편을 촬영할 때는 [DataKeeper 60초 데모 촬영 시나리오](VIDEO-DEMO-60S.md)를 사용한다. 이 문서는 상세한 리허설, 예외 대응과 원상복구를 위한 확장 운영 가이드다.

이 시나리오는 DataKeeper의 세 화면인 **분류·학습**, **권한 기반 질문**, **판정·접근 로그**를 약 5분 안에 보여 주기 위한 촬영용 대본이다. 핵심 메시지는 다음 네 가지다.

1. 문서를 섹션별 `O(Open)`, `S(Sensitive)`, `C(Classified)`로 분류한다.
2. 사용자는 자신의 `access_grade` 이하이면서 분류가 확정된 섹션만 조회할 수 있다.
3. 사용자가 등급과 근거를 수정·확정하면 Classification Skill이 생성되어 다음 업로드 분류에 반영된다.
4. 접근 로그에는 사용자·등급·동작·섹션 ID·허용/제외 개수만 남고 질문, 답변, 프롬프트, 섹션 원문은 남지 않는다.

모든 샘플의 회사명, 프로젝트명, 수치, 일정과 계약 조건은 가상이다. 실제 개인정보, 비밀번호, API 키 또는 영업비밀은 사용하지 않는다.

## 촬영용 샘플 문서

| 파일 | 화면 제목 | 보여 줄 등급과 핵심 키워드 |
|---|---|---|
| `data/uploads/01_cso_product_brief.md` | Project Aster 제품 브리프 | O: Aster Lens 공개 체험, S: Atlas 캠페인 예산, C: Polaris Score·Helios 복구 모드 |
| `data/uploads/02_orion_contract_review.md` | Project Orion 파트너 계약 검토안 | O: 외부 공유용 협력 개요, S: 기본 계약·SLA·승인 경로, C: 협상 하한선, 사용자 수정 대상: 해지 조건 등급 검토 메모 |

첫 번째 문서는 촬영 전에 올려 두고, 두 번째 문서를 영상에서 직접 업로드하는 구성이 가장 안정적이다. 업로드 대기 시간이 길면 해당 구간만 점프 컷한다.

임시 DB에서 Gemini 분류를 두 번 실측했을 때 Aster는 `O/O/S/S/C/C/O`로 모두 자동 확정됐고, Orion은 `O/S/S/S/C/S/S/O`로 제안됐다. 두 번 모두 Orion의 `해지 조건 등급 검토 메모`만 신뢰도 `75%`의 `pending_review`였다. 두 문서의 파생 문서 등급은 C였다. 실제 촬영 환경에서도 비슷한 결과가 예상되지만 모델 출력이므로 고정값으로 전제하지 않고 아래 대체 동선을 함께 준비한다.

## 사전 준비 체크리스트

### 데이터와 복구 지점

- [ ] 저장소 루트에서 두 샘플 파일이 존재하는지 확인한다.
- [ ] `datakeeper.db`를 촬영 직전 상태로 백업하고 출력된 **절대 경로를 별도로 기록**한다.
- [ ] 기존 업로드·수정·Skill·로그를 보존하기 위해 `python -m app.init_samples --reset`은 실행하지 않는다.
- [ ] 리허설 흔적을 없애야 한다면 전체 초기화 대신 촬영 전 백업으로 복구한 뒤 다시 준비한다.
- [ ] 녹화 중 다른 사용자가 같은 DB를 수정하지 않는지 확인한다.

```bash
test -f data/uploads/01_cso_product_brief.md
test -f data/uploads/02_orion_contract_review.md
.venv/bin/python -c 'from app.db import backup_database; print(backup_database())'
```

### API 키와 앱 실행

- [ ] 라이브 문서 분류용 `GEMINI_API_KEY` 또는 `GOOGLE_API_KEY`가 `.env`에 설정되어 있는지 확인한다.
- [ ] 생성형 답변을 시연하려면 `ACE_PROVIDER`에 맞는 Gemini 또는 Anthropic 키도 확인한다. 키가 없거나 호출이 실패해도 UI는 자동으로 권한 기반 키워드 검색 결과로 전환된다.
- [ ] `.env`나 터미널의 키 값은 화면에 노출하지 않는다.
- [ ] React 빌드 후 서버를 실행하고 API 응답을 확인한다.

```bash
cd app/web
npm run build
cd ../..
.venv/bin/uvicorn app.server:app --port 8000
```

별도 터미널에서 다음을 확인한다.

```bash
curl -fsS http://127.0.0.1:8000/api/personas
curl -fsS http://127.0.0.1:8000/api/classifications
```

### 프리롤 상태 만들기

- [ ] `http://127.0.0.1:8000`을 열고 브라우저 배율을 90~100%로 맞춘다.
- [ ] 촬영은 대화 이력이 없는 새 탭에서 시작한다. 기존 탭을 사용한다면 등장할 각 persona에서 `현재 대화 지우기`를 먼저 누른다.
- [ ] **분류·학습**에서 `01_cso_product_brief.md`를 미리 업로드한다.
- [ ] `공개 체험 일정`과 `내부 출시 운영안`이 각각 O, S로 보이는지 확인한다. 둘 중 하나가 `확인 필요`라면 실제 의미에 맞게 O 또는 S로 확정해 둔다.
- [ ] Project Aster의 `공개 체험 일정`과 `내부 출시 운영안`이 질문에서 조회 가능한 상태인지 한 번 확인한다.
- [ ] Project Orion은 영상에서 업로드할 것이므로 촬영 전 문서함에 없는 편이 좋다. 리허설로 이미 생성했다면 촬영 전 백업 상태로 되돌린다.
- [ ] 우측 **학습된 Skill**의 시작 개수를 메모한다. 영상에서는 수정 후 이 값이 1 증가하는지 보여 준다.
- [ ] 알림, 메신저, 자동 완성 팝업을 끄고 마우스 포인터 강조와 1080p 이상 녹화를 설정한다.

> 자동 분류 결과와 답변 문장은 모델에 따라 조금 달라질 수 있다. 영상에서 검증할 불변 조건은 답변 문구가 아니라 `사용자 등급 이상의 출처가 나타나지 않는 것`, `pending_review가 조회되지 않는 것`, `수정 후 Skill과 감사 로그가 생성되는 것`이다.

## 복사해서 사용할 입력 문구

등급 수정 근거:

```text
해지권은 향후 협상 전략과 결렬 기준을 노출하므로 C
```

권한별 질문:

```text
웹 체험은 10월 12일 어디서 신청하나요?
30일 넘게 중단되면 즉시 해지할 수 있나요?
```

두 번째 질문은 Project Orion의 검수 대기 섹션에만 있는 `30일`, `넘게`, `중단되면`, `즉시`, `해지할`을 함께 사용한다. 순수 검색으로 검증했을 때 확정 전에는 O/S/C 모두 0건이고, C로 사용자 확정한 뒤에는 O/S가 0건, CEO가 해당 C 섹션 1건이었다.

S 등급의 정상 조회까지 추가 촬영하려면 다음 질문을 사용한다.

```text
Atlas 캠페인 4,800만 원과 QA 4명 배치 계획은?
```

## 5분 녹화 대본

### 00:00–00:25 — 문제와 해결 방식 소개

**화면 조작**

- 앱 첫 화면에서 상단의 세 메뉴 `분류·학습`, `권한 기반 질문`, `판정·접근 로그`를 차례로 가리킨 뒤 `분류·학습`에 머문다.
- 상단 지표와 O/S/C 배지가 한 화면에 보이도록 한다.

**내레이션**

> DataKeeper는 문서를 통째로 공개하거나 차단하지 않습니다. 문서를 의미 단위 섹션으로 나누고, 공개 O, 민감 S, 기밀 C 등급을 부여합니다. 사용자는 자신의 등급 이하인 확정 섹션만 검색과 답변에 사용할 수 있습니다.

**예상 결과**

- `자동 판정부터 학습까지` 제목과 분류 문서·전체 섹션·확인 필요·활성 Skill 지표가 보인다.
- 문서함, 가운데 섹션 목록, 우측 학습된 Skill 영역이 함께 보인다.

### 00:25–00:50 — 섹션 분류와 문서 최고 등급

**화면 조작**

- 문서함에서 `Project Aster 제품 브리프`를 선택한다.
- O `공개 체험 일정`, S `내부 출시 운영안`, C `핵심 추천 로직` 카드를 빠르게 스크롤하며 보여 준다.
- 상단 `문서 최고 등급 C`와 안내 문구를 가리킨다.

**내레이션**

> 같은 문서 안에도 공개 일정, 내부 예산, 핵심 알고리즘처럼 민감도가 다른 내용이 섞여 있습니다. 문서 표시는 섹션 중 가장 높은 C지만, 실제 접근 판정은 섹션마다 따로 수행됩니다. 그래서 C 문서 안의 O 정보는 외부 고객도 안전하게 활용할 수 있습니다.

**예상 결과**

- 한 문서 안에 O/S/C 카드가 함께 보인다.
- 문서 등급은 섹션 등급의 최댓값인 C로 보인다.
- `확인 필요` 섹션은 등급 배지가 있어도 확정 전에는 접근 차단 대상이다.

### 00:50–01:25 — Project Orion 라이브 업로드

**화면 조작**

- 왼쪽 `문서 추가`를 클릭한다.
- `data/uploads/02_orion_contract_review.md`를 선택한다.
- `섹션을 나누고 CSO 등급을 판정하고 있습니다` 상태를 1~2초 보여 준 뒤 필요하면 점프 컷한다.
- 완료 후 문서함의 `Project Orion 파트너 계약 검토안`을 선택하고 섹션 목록을 천천히 훑는다.

**내레이션**

> 계약 검토안을 업로드해 보겠습니다. 분류 모델은 섹션마다 등급, 신뢰도, 요약, 키워드와 판단 근거를 제안합니다. 신뢰도가 80%보다 낮으면 확인 필요 상태로 남고, 사용자 확인 전에는 누구에게도 제공되지 않습니다.

**예상 결과**

- 업로드 완료 메시지에 `문서 C 등급 · 확인 필요 1개`가 표시될 것으로 예상된다.
- 외부 공유 개요, 계약 조건, SLA, 독점 우선협상권, 협상 하한선, 해지 조건 검토 메모 등이 별도 섹션으로 보인다.
- 실측 2회에서는 `해지 조건 등급 검토 메모`만 S, 신뢰도 75%, `확인 필요`였고 나머지는 자동 확정됐다.

### 01:25–01:55 — C 사용자도 검수 대기 정보는 차단

**화면 조작**

- `권한 기반 질문`으로 이동해 `CEO` C를 선택한다.
- 우측에서 O/S/C 모두 `조회 가능`임을 보여 준다.
- 다음 질문을 입력한다.

```text
30일 넘게 중단되면 즉시 해지할 수 있나요?
```

**내레이션**

> CEO는 C까지 접근할 수 있지만, 등급이 제안됐다는 사실만으로 원문이 열리지는 않습니다. 신뢰도가 낮아 확인 필요인 섹션은 사용자 등급과 관계없이 기본 차단합니다.

**예상 결과**

- `접근 가능한 범위에서 질문과 관련된 자료를 찾지 못했습니다` 안내가 나타난다.
- 출처 카드와 30일 해지 조건이 표시되지 않는다.
- 이는 C 권한 부족이 아니라 `pending_review` 상태 때문이며, 해당 질문은 실측에서 확정 전 O/S/C 모두 0건이었다.

### 01:55–02:35 — S 제안을 C로 수정하고 Skill 생성

**화면 조작**

- `분류·학습`으로 돌아가 `Project Orion 파트너 계약 검토안`을 다시 선택한다.
- `해지 조건 등급 검토 메모` 카드의 `검토하기`를 누른다.
- C를 선택한다.
- 수정 근거 칸에 아래 문장을 붙여 넣는다.

```text
해지권은 향후 협상 전략과 결렬 기준을 노출하므로 C
```

- `등급 확정`을 누른다.
- 카드의 `사용자 확정` 상태와 우측 `학습된 Skill` 영역의 새 카드 및 활성 개수 증가를 차례로 가리킨다.

**내레이션**

> 자동 판정은 제안이고 최종 기준은 조직이 결정합니다. 30일 중단 시 즉시 해지할 수 있다는 조건은 향후 협상 전략과 결렬 기준을 드러내므로 S 제안을 C로 수정하겠습니다. 이 수정은 단순 덮어쓰기가 아닙니다. 근거와 키워드가 활성 Classification Skill로 저장되어 이후 업로드의 분류 프롬프트에 반영됩니다.

**예상 결과**

- 실측과 같다면 S·확인 필요에서 C·사용자 확정으로 바뀐다.
- 성공 알림이 나타나고 활성 Skill 개수가 1 증가한다.
- 새 Skill은 해당 섹션 제목과 C 배지, 사용자 피드백 설명을 포함한다.
- 이 Skill은 **다음 업로드부터** 사용되며 기존 다른 섹션을 소급해 자동 변경하지 않는다.

> 모델이 처음부터 C로 판정했다면 등급을 일부러 낮추지 않는다. C를 유지하고 같은 조직 근거로 확정하면서 “자동 판단을 사람의 정책으로 확정하고 재사용 가능한 Skill로 만든다”고 설명한다. 자동 S였지만 이미 확정 상태라면 그대로 C로 수정해도 된다.

### 02:35–03:00 — O 사용자: 공개 정보만 조회

**화면 조작**

- `권한 기반 질문`으로 이동한다.
- `외부 고객` O를 선택한다.
- 우측 접근 정책에서 O는 `조회 가능`, S/C는 `조회 제외`임을 가리킨다.
- 다음 질문을 입력한다.

```text
웹 체험은 10월 12일 어디서 신청하나요?
```

**내레이션**

> 먼저 O 등급 외부 고객입니다. 공개 섹션만 검색 대상이 되고 S와 C 원문은 검색 단계부터 제외됩니다.

**예상 결과**

- 공식 소개 페이지에서 신청할 수 있다는 내용을 안내한다.
- 사용 근거가 표시되면 O 섹션만 나타난다.
- 답변 문장이 달라져도 S/C 출처가 나타나면 안 된다.

### 03:00–03:25 — S 사용자: 방금 확정한 C 정보 차단

**화면 조작**

- `영업팀원` S를 선택한다.
- 외부 고객의 transcript는 해당 프로필에 저장된 채 숨겨지고, 영업팀원의 마지막 transcript가 복원되거나 저장 이력이 없으면 빈 대화가 표시되는 것을 확인한다.
- 우측에서 O/S는 `조회 가능`, C는 `조회 제외`임을 가리킨다.
- 다음 질문을 입력한다.

```text
30일 넘게 중단되면 즉시 해지할 수 있나요?
```

**내레이션**

> 영업팀원은 O와 S까지 사용할 수 있지만 방금 C로 확정한 해지 조건은 후보 검색과 LLM 컨텍스트에서 빠집니다. 내용을 낮은 등급으로 요약하거나 일부만 마스킹하지 않고 섹션 자체를 제외합니다.

**예상 결과**

- `접근 가능한 범위에서 질문과 관련된 자료를 찾지 못했습니다` 안내가 나타난다.
- C 출처 카드와 30일 해지 조건은 표시되지 않는다.
- 실측에서는 C 확정 후에도 O/S 사용자는 이 질문에 0건이었다.
- CEO로 전환하기 전에 이 결과 화면을 충분히 촬영한다. 사용자 변경 후에도 이 결과는 영업팀원 transcript에 보존되며 CEO 대화에는 표시되지 않는다.

### 03:25–03:50 — C 사용자: 같은 질문 허용

**화면 조작**

- `CEO` C를 선택한다.
- S 대화가 숨겨지고 CEO의 마지막 transcript가 복원되는지 보여 준다. 촬영 준비에서 CEO 대화를 비웠다면 빈 상태가 표시된다.
- 우측에서 O/S/C가 모두 `조회 가능`임을 보여 준다.
- 바로 전과 같은 질문을 다시 보낸다.

```text
30일 넘게 중단되면 즉시 해지할 수 있나요?
```

**내레이션**

> 같은 질문을 C 등급 CEO로 다시 실행합니다. 질문이 아니라 사용자 권한과 확정된 섹션 등급이 결과를 결정합니다.

**예상 결과**

- 서비스 공급이 30일 넘게 중단되면 즉시 해지할 수 있다는 내용을 안내한다.
- 사용 근거에 C `해지 조건 등급 검토 메모`가 정확히 1건 나타난다.
- CEO transcript에는 앞선 S 사용자 결과가 섞이지 않는다. S로 돌아가면 앞선 S 결과가 다시 복원되며, 비교 장면은 사용자 전환 전후의 연속 컷으로 구성한다.

### 03:50–04:35 — 분류·접근 감사 로그와 내용 비기록

**화면 조작**

- `판정·접근 로그`로 이동하고 `새로고침`을 누른다.
- `등급 판정 로그`에서 방금 섹션의 `corrected` 또는 `confirmed`, 이어지는 `skill_created` 항목을 가리킨다.
- `접근 로그` 탭을 누르고 외부 고객 O, 영업팀원 S, CEO C의 최근 항목을 보여 준다.
- 화면 우측 상단의 `질문·답변 미표시`와 `내용 비기록` 원칙을 가리킨다.

**내레이션**

> 분류 이력에는 누가 어떤 등급을 어떤 근거로 확정했고 어떤 Skill이 생성됐는지 남습니다. 접근 로그에는 사용자, 접근 등급, 실행 동작, 사용한 섹션 식별자와 허용·제외 개수만 기록합니다. 질문, 답변, 프롬프트와 섹션 원문은 감사 로그에 저장하지 않습니다.

**예상 결과**

- 최신 분류 로그에 사용자 수정·확정과 Skill 생성 이벤트가 보인다.
- 최신 접근 로그에 `external/O`, `sales_rep/S`, `ceo/C`에 대응하는 사용자와 사용/제외 개수가 보인다.
- 채팅 화면에서 입력한 질문 문장이나 생성된 답변 본문은 접근 로그에 나타나지 않는다.
- `허용 섹션`은 해당 검색·답변에 실제 사용된 섹션 수이고, `권한 밖` 수는 질문 매칭 건수가 아니라 당시 전체 지식베이스에서 해당 사용자가 읽을 수 없던 섹션 수다.

### 04:35–05:00 — 마무리

**화면 조작**

- 접근 로그에서 세 화면 메뉴가 보이는 상단으로 시선을 옮긴다.
- 마지막 프레임은 `분류·학습`의 O/S/C 섹션과 학습된 Skill이 함께 보이는 화면으로 끝낸다.

**내레이션**

> DataKeeper는 자동 분류, 사람의 정책 보정, 섹션 단위 접근 제어, 그리고 내용 없는 감사 추적을 하나의 흐름으로 연결합니다. 공개 정보는 활용하고 기밀 정보는 권한 밖의 검색과 AI 컨텍스트에서 처음부터 제외합니다.

## 선택 옵션: 기존 데이터가 많을 때의 클린 촬영

기본 동선은 현재 DB를 그대로 보존하는 것이다. 기존 문서와 검수 대기 항목이 너무 많아 화면 전달력이 떨어질 때만 아래 절차를 **격리된 로컬 촬영 환경에서 선택적으로** 사용한다.

> 경고: `app.init_samples --reset`은 현재 업로드 문서, 분류 수정, Skill, 로그를 모두 삭제한다. 공유 DB나 운영 DB에서는 실행하지 않는다. 촬영 중 다른 쓰기가 발생하면 백업 복구 시 그 변경도 사라지므로 반드시 단독 사용 환경이어야 한다.

1. 서버를 멈춘다.
2. 앞의 `backup_database()` 명령으로 백업하고 절대 경로와 생성 시각을 확인한다.
3. 복구 연습까지 끝났고 해당 백업이 유효할 때만 샘플 DB를 만든다.

```bash
.venv/bin/python -m app.init_samples --reset
```

4. Aster를 프리롤로 업로드하고 Orion은 촬영 중 업로드한다.
5. 촬영이 끝나면 아래 **촬영 후 원상복구** 절차로 백업 전체를 되돌린다.

## 촬영 후 원상복구

가장 확실한 원상복구는 촬영 전에 만든 SQLite 백업을 되돌리는 것이다. 이 방식은 데모 문서뿐 아니라 촬영 중 생긴 Skill과 감사 로그까지 정확히 촬영 전 상태로 복원한다.

1. Uvicorn 서버를 종료하고 같은 DB를 쓰는 다른 프로세스가 없는지 확인한다.
2. 사전 준비에서 기록한 백업 절대 경로를 다시 확인한다.
3. 아래 명령의 마지막 인자를 **실제 백업 절대 경로**로 바꿔 실행한다.

```bash
.venv/bin/python -c 'import sqlite3,sys; source=sqlite3.connect(sys.argv[1]); target=sqlite3.connect("datakeeper.db"); source.backup(target); target.close(); source.close()' /absolute/path/to/datakeeper.backup-YYYYMMDDTHHMMSSffffffZ.db
```

4. 무결성을 확인하고 서버를 다시 실행한다.

```bash
.venv/bin/python -c 'from app.db import get_conn; conn=get_conn(); print(conn.execute("PRAGMA integrity_check").fetchone()[0]); conn.close()'
.venv/bin/uvicorn app.server:app --port 8000
```

`PRAGMA integrity_check` 결과가 `ok`여야 한다.

백업 전체를 되돌릴 수 없는 경우에는 문서함의 휴지통으로 이번 촬영에서 추가한 Project Aster와 Project Orion만 삭제할 수 있다. 다만 감사 추적 설계상 문서를 삭제해도 내용 없는 분류·접근 로그는 보존되고, 생성된 Skill도 자동 삭제되지 않으므로 이것은 완전한 원상복구가 아니다. 기존 DB를 보존하려면 전체 `--reset`보다 촬영 직전 백업 복원을 우선한다.

## 최종 촬영 확인표

- [ ] O/S/C가 각각 최소 한 번 화면에 선명하게 보였다.
- [ ] `pending_review`는 확정 전 차단된다는 설명이 들어갔다.
- [ ] C 권한 CEO도 `pending_review` 해지 조건을 보지 못하는 장면을 담았다.
- [ ] 해지 조건 등급 검토 메모를 S에서 C로 수정 또는 확정했다.
- [ ] 우측 활성 Skill 개수가 증가하는 장면을 담았다.
- [ ] 외부 고객 O, 영업팀원 S, CEO C의 정책 차이를 보여 줬다.
- [ ] 동일한 C 질문에 S와 C 사용자의 결과가 달랐다.
- [ ] 접근 로그에 질문과 답변 내용이 없음을 보여 줬다.
- [ ] API 키, 개인 알림, 실제 고객 정보가 화면에 노출되지 않았다.
- [ ] 촬영 후 백업을 이용해 DB를 원상복구했다.
