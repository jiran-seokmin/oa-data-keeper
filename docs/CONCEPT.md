# DataKeeper — C/S/O 분류·접근 제어 컨셉

> **DataKeeper** — All Data, Safe for Everyone (모든 데이터를, 모두가 안전하게) · 지란지교소프트
> 최종 갱신: 2026-08-30

한 줄 정의: **문서를 섹션 단위로 O/S/C 분류하고, 확정 상태와 사용자의 접근 등급을 결정론적으로
비교해 원문 접근을 허용하거나 차단하는 AI 지식 서비스.**

## 1. 해결하려는 문제

사내 문서 하나에는 공개 안내, 내부 운영 정보, 기밀 의사결정이 함께 들어갈 수 있다. 문서 전체에
하나의 권한만 붙이면 과도하게 막거나 과도하게 열게 된다. 이 문서를 AI 지식 서비스에 연결하면
검색 결과뿐 아니라 LLM 컨텍스트로 들어가는 데이터도 같은 문제를 가진다.

기존 방식의 주요 한계는 다음과 같다.

| 접근 | 한계 |
|---|---|
| 내부용·외부용 지식봇 분리 | 데이터 복제, 동기화 비용, 정책 불일치 |
| 문서 단위 권한 | 한 문서 안의 서로 다른 민감도를 표현하지 못함 |
| 질문 이후 필터링 | 권한 밖 원문이 검색 또는 LLM 단계에 먼저 들어갈 수 있음 |
| 자동 분류만 신뢰 | 오분류를 고칠 운영 흐름과 이력이 없음 |
| 전체 질문·답변 감사 저장 | 감사 로그 자체가 새로운 민감 데이터 저장소가 됨 |

DataKeeper의 핵심 선택은 **섹션 단위 분류, 권한 필터 우선, 이진 접근, 사용자 피드백, 내용 없는
감사**다.

## 2. 핵심 모델

### 2.1 공통 등급

데이터와 사용자에게 같은 순서의 세 등급을 사용한다.

| 등급 | 이름 | 데이터 의미 | 사용자 의미 |
|---|---|---|---|
| O | Open · 공개 | 외부 공개 가능 | 공개 정보 접근 |
| S | Sensitive · 민감 | 조직 내부 제한 | O와 S 정보 접근 |
| C | Classified · 기밀 | 중대한 영향 정보 | O, S, C 정보 접근 |

순서는 O < S < C다. 런타임 정책은 부서, 직무, 질문 종류로 등급을 완화하지 않는다. persona의
department와 channel은 표시·향후 연동을 위한 메타데이터이며 현재 접근 결과를 바꾸지 않는다.

### 2.2 분류 상태

| 상태 | 의미 | 접근 |
|---|---|---|
| auto_confirmed | 신뢰도 기준을 통과한 자동 분류 | 등급 비교 후 허용 가능 |
| user_confirmed | 사용자가 근거와 함께 확정한 분류 | 등급 비교 후 허용 가능 |
| pending_review | 검토가 필요한 제안 또는 미분류 | 항상 차단 |

상태 누락, 알 수 없는 상태, 잘못된 등급도 항상 차단한다. 이는 오류가 발생했을 때 더 넓은 권한을
선택하지 않는 fail-closed 원칙이다.

### 2.3 접근 판정

    confirmed = section.classification_status가 확정 상태인가
    enough     = section.grade의 순위 <= persona.access_grade의 순위
    allowed    = confirmed AND enough

결과는 allowed 또는 denied 하나다.

- allowed이면 원문을 검색 결과와 답변 컨텍스트에 사용할 수 있다.
- denied이면 섹션 원문과 메타데이터를 사용자용 검색 후보에서 제외한다.
- LLM은 판정을 재해석하거나 예외를 만들 수 없다.

### 2.4 문서 등급

문서 등급은 소속 섹션 등급의 최댓값이다. 한 섹션이 C이면 문서 표시 등급도 C다. 이 값은 조회
시 계산하고 documents 테이블에는 저장하지 않는다. 따라서 섹션 분류를 고치면 문서 등급도 즉시
바뀌고, 중복 상태가 어긋날 가능성이 없다.

pending_review 섹션에 제안 등급이 있으면 문서 최고 등급 표시에는 반영될 수 있지만, 그 섹션
원문은 확정 전까지 접근할 수 없다. 등급이 없는 섹션은 최댓값 계산에서 제외되고 자체 접근은
차단된다.

## 3. 시스템 흐름

    [정적 samples 또는 txt/md 업로드]
                    │
                    ▼
       섹션 분리 → 등급·신뢰도·근거·요약·키워드
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
      확정 분류           pending_review
          │                   │
          │             사용자 확정·수정
          │                   │
          └─────────┬─────────┘
                    ▼
          SQLite sections + 분류 로그
                    │
         persona.access_grade와 비교
                    │
          허용 섹션만 SQL에서 조회
                    │
          키워드 검색 → 선택적 LLM 답변
                    │
          식별자·판정 수치만 접근 로그

### 3.1 정적 샘플

app.seed_db의 검토된 등급 시드는 source_section_id를 통해 각 문단 섹션에 적용된다. 검토된
샘플은 user_confirmed로 저장한다. 시드가 없는 섹션은 grade를 비워 pending_review로 저장하므로
실수로 공개되지 않는다.

app.init_samples --report는 DB를 쓰지 않고 시드 누락과 고아 항목을 검사한다. --reset은 현재
DB를 완전히 재생성하므로 업로드 문서, 사용자 수정, Skill, 감사 로그도 제거한다. 데모 데이터
복원이 명확히 필요할 때만 실행한다.

### 3.2 런타임 업로드 분류

1. txt 또는 md 문서를 의미 단위 섹션으로 나눈다.
2. 활성 Classification Skill과 관리자 키워드 힌트를 Gemini 분류 프롬프트에 넣는다.
3. 정상 배치에서 빠진 항목은 개별 보완하고, 배치 응답 전체가 유효하지 않으면 전체 섹션을 개별 재시도한다.
4. 각 섹션에 grade, confidence, classification_reason, summary, keywords, departments를 저장한다.
5. confidence가 0.8 미만이면 pending_review, 이상이면 auto_confirmed로 저장한다.
6. auto_classified와 실제 적용된 skill_applied 이벤트를 본문 없이 기록한다.

summary는 분류 검토와 허용된 섹션의 검색 보조 메타데이터다. 권한 밖 원문을 대신 제공하는
수단으로 사용하지 않는다.

### 3.3 사용자 확정과 Skill 피드백

검토자는 섹션의 등급과 근거를 수정·확정할 수 있다. 하나의 트랜잭션에서 다음이 함께 처리된다.

- 섹션을 user_confirmed로 갱신
- confirmed_by와 confirmed_at 기록
- 이전·새 등급과 상태를 classification_logs에 기록
- 섹션 제목, 키워드, 사용자가 입력한 근거를 기반으로 피드백 Skill 생성 또는 갱신

Skill에는 섹션 원문을 넣지 않는다. 활성 Skill은 이후 업로드 분류에 제공되고, 분류기는 실제로
적용한 Skill 이름을 결과와 감사 이벤트에 남긴다.

### 3.4 검색과 답변

1. 서버가 persona를 조회한다.
2. SQL이 확정 상태이면서 사용자 등급 이하인 섹션만 읽는다.
3. 허용된 섹션의 제목, 원문, 요약, 키워드에 현재 질문 토큰을 먼저 매칭한다.
4. 현재 질문이 단독으로 매칭되지 않으면 같은 persona의 최근 질문 최대 5개와 결합해 한 번 더 검색한다. 이 경우에도 허용 섹션 밖의 원문은 검색 후보에 없다.
5. 보완 검색까지 결과가 없으면 접근 가능한 범위에서 자료가 없다고 답한다.
6. /api/search는 허용된 결과를 그대로 반환한다.
7. /api/chat은 동일한 허용 원문과 이전 질문 문맥만 LLM에 넣으며, 과거 답변은 다시 전달하지 않는다.

프런트엔드는 LLM 자격 증명이 없거나 생성이 실패하면 검색 결과로 폴백한다. 이 폴백도 같은
권한 필터를 사용한다.

### 3.5 내용 없는 감사

classification_logs에는 섹션·문서 식별자, 동작, actor, 이전·새 등급과 상태, 근거, 신뢰도,
Skill 식별자를 저장한다. access_logs에는 persona 식별자, 당시 접근 등급, 동작, 문서·사용 섹션
식별자, 허용·차단 개수와 시각을 저장한다.

질문, 답변, 프롬프트, 섹션 원문은 두 감사 로그에 저장하지 않는다. 문서를 삭제하면 섹션과 원문은
제거되지만 기존 로그의 내용 없는 문서 메타데이터는 남고 section_id 외래 키는 NULL이 된다.

## 4. 데이터 모델

### documents

- doc, doc_title, source_path, created_at, updated_at
- grade 컬럼 없음

### sections

- 구조: id, doc, seq, title, parent_title, source_section_id, text
- 분류: grade, confidence, classification_status, classification_reason, summary
- 보조: keywords, departments
- 확인: confirmed_by, confirmed_at
- 생성·수정 시각

### personas

- id, name, access_grade, department, channel, 생성·수정 시각

### classification_skills

- 이름, 설명, 분류 지침, 선택 등급, 키워드, 예시, 활성 상태, 생성자와 시각

### classification_logs

- 분류 이벤트에 필요한 식별자·상태·근거만 저장

### access_logs

- 접근 이벤트에 필요한 사용자·등급·동작·식별자·개수만 저장

### runtime_state

- 브라우저 탭의 채팅 transcript를 일괄 무효화하는 불투명 세대 값만 저장
- 질문·답변과 사용자 식별 정보는 저장하지 않음

모든 리스트 필드는 SQLite에서 유효한 JSON 배열로 검사한다. 확정 상태는 유효한 grade를 가져야
하며 user_confirmed는 확인자와 확인 시각을 가져야 한다.

운영 정리 명령은 문서·섹션·persona와 현재 분류 상태를 보존한 채 Classification Skill과 두 감사
로그를 삭제하고 runtime_state의 채팅 세대를 교체한다. 클라이언트는 세대 변경을 감지하면 각 탭의
모든 persona transcript를 삭제한다. search/chat은 클라이언트가 확인한 세대를 함께 보내며, 서버는
접근 로그를 쓰기 직전에 다시 비교해 정리 이전 요청이 새 로그를 남기지 못하게 한다.

## 5. 신뢰 경계와 안전 속성

### 접근 제어는 LLM 앞에서 끝난다

store.load_accessible_sections는 권한 밖 원문을 Python 객체로 만들기 전에 SQL에서 제외한다.
검색과 답변 생성은 이 반환값만 사용한다. 프롬프트 지시로 접근 등급이나 분류 상태를 바꿀 수 없다.

### 분류와 접근을 분리한다

LLM의 역할은 등급 제안이다. 접근은 engine.decide의 고정 순서 비교다. 분류가 불확실하면 낮은
신뢰도와 pending_review로 보내고, 접근 엔진은 이를 무조건 차단한다.

### 관리 화면과 사용자 화면을 분리한다

분류 화면은 전체 분류 메타데이터를 관리하기 위한 화면이고, 사용자 문서·질문 API는 허용된
섹션만 반환한다. 현재 데모에는 인증이 없으므로 이 경계는 제품화 전에 관리자 인가로 강제해야 한다.

### 파생 상태를 최소화한다

문서 등급을 저장하지 않고 섹션에서 계산한다. 감사 로그에는 본문을 복제하지 않는다. 데이터
삭제와 등급 수정 후에도 서로 다른 사본이 어긋날 가능성을 줄인다.

## 6. 기존 DB 마이그레이션

레거시 섹션 등급은 D0 → O, D1~D3 → S, D4 → C로 변환한다. 기존 사용자 숫자 clearance는
0 → O, 1~3 → S, 4 → C로 변환한다. 기존 needs_review 또는 등급 누락 섹션은
pending_review로 유지해 보수적으로 차단한다.

app.migrate_cso는 다음 순서를 지킨다.

1. 스키마를 검사하고 지원하지 않는 부분 스키마를 거부한다.
2. 기본적으로 SQLite backup API로 datakeeper.backup-타임스탬프.db를 만든다.
3. 문서·섹션·persona를 한 트랜잭션에서 새 테이블로 옮긴다.
4. 각 기존 섹션에 legacy_migrated 분류 로그를 남긴다. 로그에는 원문이 없다.
5. 외래 키 검사를 통과한 뒤 커밋한다.

서버 초기화는 기존 스키마를 자동으로 바꾸지 않는다. 운영자는 복제본에서 먼저 아래 명령을
검증하고 백업 경로를 확인한 뒤 실제 DB에 적용한다.

    python -m app.migrate_cso --db datakeeper.db

백업을 생략하는 옵션은 폐기 가능한 테스트 DB에서만 사용한다.

## 7. 데모 시나리오

샘플 persona는 외부 고객 O, 신입 개발자·영업팀원·영업팀장 S, CEO C다. 부서가 같더라도 현재
판정은 등급만 비교한다.

| 섹션 상태 | O 사용자 | S 사용자 | C 사용자 |
|---|---|---|---|
| 확정 O | 허용 | 허용 | 허용 |
| 확정 S | 차단 | 허용 | 허용 |
| 확정 C | 차단 | 차단 | 허용 |
| pending_review | 차단 | 차단 | 차단 |

추천 시연 흐름:

1. 분류·학습 화면에서 문서 최고 등급과 섹션별 근거를 확인한다.
2. 검토 대기 섹션을 다른 등급과 근거로 확정한다.
3. Skill이 생성되고 분류 로그에 변경 이력이 남는지 확인한다.
4. 서로 다른 persona로 같은 질문을 보내 근거 섹션이 달라지는지 확인한다.
5. 접근 로그에 질문 본문 없이 사용 섹션 수와 차단 수만 남는지 확인한다.

## 8. 구현 범위

### 구현됨

- 섹션 단위 O/S/C 스키마와 이진 판정 엔진
- 검토 대기 default-deny
- 정적 샘플 시딩과 Gemini 업로드 분류
- 사용자 확정·수정과 Classification Skill 피드백
- 분류·접근 감사 로그
- 권한 필터 우선 키워드 검색
- 허용 원문만 사용하는 Gemini 또는 Anthropic 답변
- FastAPI와 React 분류·질문·로그 UI
- 안전한 DB 백업·마이그레이션

### 데모 한계

- 로그인, SSO, 서버 검증 조직 권한 없음
- 관리자 API와 사용자 API의 역할 기반 인가 없음
- SQLite 키워드 부분 일치만 사용하며 벡터 검색은 없음
- 업로드는 txt와 md, Gemini 분류만 지원
- 감사 보존·내보내기·위변조 방지 정책 없음
- React 자동화 테스트와 완전한 API 계약 테스트 부족

## 9. 기술 스택

| 레이어 | 구현 |
|---|---|
| 분류 LLM | Gemini 구조화 출력, 문서 배치 우선 |
| 접근 엔진 | 순수 Python, 고정 등급 순서 |
| 저장 | SQLite, JSON 검사와 외래 키 |
| 검색 | 권한 필터 이후 Python 토큰 부분 일치 |
| 답변 LLM | Gemini 기본, Anthropic 선택 |
| API | FastAPI + Pydantic |
| UI | React 19 + TypeScript + Vite |

## 10. 주요 리스크와 대응

| 리스크 | 현재 대응 | 제품화 과제 |
|---|---|---|
| 분류 오류 | 신뢰도 임계값, pending_review, 사용자 확정 | 평가 데이터셋과 정기 품질 측정 |
| 등급 누락·상태 오류 | fail-closed, DB CHECK | 운영 알림과 검수 SLA |
| 권한 밖 원문 노출 | SQL 선필터, 동일 필터를 검색·챗에 재사용 | API 인가와 보안 테스트 |
| persona 위조 | 데모 DB 조회 | SSO claim과 서버 정책으로 교체 |
| 감사 로그의 민감화 | 질문·답변·원문 미저장 | 보존 기간, 접근 통제, 무결성 |
| DB 변경 실패 | 기본 백업, 트랜잭션, 외래 키 검사 | 복구 훈련과 배포 자동화 |

## 11. 확장 방향

1. 관리자와 일반 사용자 인증·인가 분리
2. 조직 시스템이 서명한 access_grade 연동
3. 검수 큐 할당, SLA, 대량 확정, 분류 품질 지표
4. Skill 승인·버전·비활성화 UI와 회귀 평가
5. 등급 메타데이터 필터가 선행되는 벡터 검색
6. 감사 로그 무결성, 보존 정책, 관리자 내보내기
7. 마이그레이션·백업·복구 자동화 테스트
